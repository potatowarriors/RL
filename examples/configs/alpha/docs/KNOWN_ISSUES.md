- **기전 — logprob 필터**: `grpo.seq_logprob_error_threshold: 2` (Ultra `swe_teacher.yaml` 과 같은 값) 가 생성 때와 학습 때 logprob 의 시퀀스 단위 오차가 큰 시퀀스를 손실에서 뺀다. `s4` 60 step 의 대상 시퀀스 2,488 개 중 10 개 (0.40%) 가 걸렸다. `s6` 의 대상은 199 · 238 개라 기대 0.80 · 0.96 개, 1 개 이상일 확률 55% · 62%, 두 step 모두일 확률 34% 다. 기준 "0" 은 step 당 64 롤아웃이던 `s4` 때 정했다. 전역 지표는 `s4` 범위 안이다 (KL 0.00162 · 0.00154, `token_mult_prob_error` 1.0226 · 1.0211). 벌점 (결정 95) 으로 새로 손실 대상이 된 한도 롤아웃이 더 잘 걸리는지는 시험하지 못했다 — 걸린 시퀀스가 무엇인지 기록이 없다.

## SWE 에이전트 컨테이너가 기동하지 못한다 — OpenHands 가 셸을 `su root -` 로 열고 uid 1100 이라 실패 (2026-11-24, ✅ 독립 검증 확인 · 대응 결정 대기)

- **증상**: 학생 롤아웃 측정 실행기를 GPU 없이 돌린 시험 (`p0_measure/swe/student_dry1` 4 과제 · 두 노드, `student_dry2` 1 과제 · 디버그 로그) 에서 5/5 롤아웃이 에이전트 로그의 `create runtime: 0.009 seconds` 뒤로 진행하지 못하고 벽시계 한도로 종료 (rc 124). 과제별 `nemo_gym_metrics.json` 에 `connect_to_runtime_time` · `initialize_runtime_time` 이 없다. 모델 호출은 한 번도 없었다. 같은 날 같은 설정의 채점 전용 컨테이너 약 1,500 개는 정상이었다.
- **원인**: Gym 이 에이전트 컨테이너를 `apptainer exec … --cleanenv …` 로 띄워 `USER` 가 비고, 우리 세션의 컨테이너는 uid 1100 이다 (root 매핑 없음). nv-OpenHands `LocalRuntime` 은 `os.getenv('USER')` 가 없으면 사용자 이름을 `root` 로 두고 (`command.py:51-55`), tmux 셸을 `su root -` 로 연다 (`bash.py:305-309`, `SU_TO_USER` 기본 true). uid 1100 의 `su root` 는 암호를 묻고 실패한다 → 셸이 없다 → action server 의 첫 초기화 명령 (`alias git=…`) 이 300 초 강제 한도까지 기다린다 → 그 초기화가 FastAPI 기동 단계 안이라 포트가 열리지 않는다 → 클라이언트의 `/alive` 대기 (300 초) 가 실패하고 다시 시도한다.
- **대조 실험 (CPU)**: 같은 컨테이너 명령 (`params.json` 의 `agent_apptainer_command_str`) 을 손으로 실행하되 띄우는 쪽 환경에 `APPTAINERENV_USER=work` 만 더했다 → `Username: work` → 셸이 `/bin/bash` 로 열림 → `connect to runtime: 15.2 s` · 초기화 1.99 s → 에이전트 첫 step 까지 감. 직접 확인: 지금 방식의 컨테이너에서 `su root -c …` 는 `Password: su: Authentication failure`, root 만 매핑한 컨테이너 (`APPTAINER_FAKEROOT=1`, uid_map `0 1100 1`) 에서도 `su: cannot set groups: Operation not permitted`.
- **선행 사례**: upstream — Gym `swe_agents/README.md:693` 이 기준 환경을 "enroot/apptainer … fakeroot" 로 적는다 (컨테이너 안 uid 0 이라 `su root -` 가 그냥 통과). upstream OpenHands 의 `LocalRuntime` 은 현재 사용자로 도는 것을 전제하고 `USER` 로 이름을 정한다. Nemotron 3 Ultra — 그 기준 환경에서 돈다. 프론티어 — 공개 안 됨. upstream 이슈는 온라인으로 찾지 않았다.
- **독립 검증**: 새 에이전트 (Opus · xhigh, 읽기 전용) 가 1단계에서 증상과 원자료만으로 같은 원인에 도달했고, 2단계 판정 **확인**. 반론 요지: ① 대조 실험이 멈춘 곳은 죽은 모델 포트가 아니라 내려간 Gym 모델 서버였다 — 모델 호출 단계는 미측정 ② 모델이 없으면 고친 뒤에도 클라이언트가 끝없이 재시도해 rc 124 로 끝난다 — GPU 없는 시험의 통과 기준은 rc 가 아니라 단계 표지 (`connect_to_runtime_time` · `initialize_runtime_time` · `GLOBAL STEP 0`) 여야 한다 ③ 대조 실험이 `student_dry2` 의 `nemo_gym_metrics.json` 을 덮어썼다 (그 디렉토리의 값은 대조 실험의 것이다) ④ 고친 쪽은 main1 에서만 봤다 ⑤ root 만 매핑하는 fakeroot 는 해법이 아니다.
- **고친 뒤에도 남는 것 (실측 11-24)**: 이 세션은 컨테이너에 바깥 `/proc` 를 넘긴다 (결정 75). 컨테이너 안의 PID 는 namespace 번호 (셸 22) 인데 `/proc/self` 는 바깥 번호 (1262013) 를 가리키고 `/proc/<자기 배경 작업 pid>` 는 없다. OpenHands 가 psutil 로 하는 일 — 컨테이너 안 메모리 감시 (`TmuxMemoryMonitor`) 와 Ctrl-C 가 안 먹는 명령의 강제 종료 (`_kill_pane_processes`) — 은 대상을 못 찾는다. `kill` 은 namespace 안에서만 풀리므로 컨테이너 밖 프로세스는 죽지 않는다. 메모리는 Gym 의 바깥 감시가 본다. 측정에서 "Kill failed" 와 멈춘 pane 을 센다.
- **대응 (결정 대기)**: `E2E_SANDBOX.md` §7.7. 후보 — ① Ray 환경에 `APPTAINERENV_USER` (코드 변경 없음, 채점 컨테이너에도 들어가므로 게이트 재확인) ② Gym 플러그인 · 패치로 에이전트 컨테이너에만 ③ 다중 uid fakeroot 로 컨테이너 안을 root 로 (미시험).
- **교훈**: 정답 패치 검증은 채점 컨테이너만 탄다 — 에이전트 컨테이너 경로는 GPU 를 잡기 전에 따로 돌려 봐야 드러난다. GPU 없는 시험의 "실패" 가 기대한 실패인지 단계 표지로 확인한다 (처음엔 "모델이 없어서" 로 읽었다).

## Apptainer 요청 사양 리허설 — 시험 도구 교착 · 의도하지 않은 이미지 내려받기 · 근거 없는 결론 셋 (2026-11-20, ✅ 정리 · 결론 철회)

- **증상**: (1) gpu06 `alpha-eval` 에서 `strace -f -Z` 로 Apptainer 실행을 통째로 추적하던 시험이 멈췄다. 내 시험 프로세스 6개 (strace 는 D 상태, FUSE 데몬과 컨테이너 프로세스는 ptrace 정지) 가 약 11분 남았고 `docker kill` 로 죽지 않았다. (2) 읽기 전용으로 의도한 상태 확인에서 `docker run ubuntu:24.04` 가 이미지를 내려받았다 (공용 서버 디스크 117 MB). (3) 보고에 근거 없는 결론을 셋 적었다 — "다중 uid 매핑은 CAP_SYS_ADMIN 이 있어야만 된다" · "커널 6.5 에서는 커널 overlayfs 를 쓴다" · "실제 이미지 실행이 막힌 syscall 을 시도하지 않는다".
- **원인**: (1) strace 가 tracee 의 메모리를 읽을 때 그 페이지가 FUSE 위의 파일이면 FUSE 데몬이 응답해야 한다. 그 데몬은 같은 strace 의 ptrace 요청 중이라 얼어 있고 SIGKILL 도 받지 못한다. (2) `docker run` 은 로컬에 없는 이미지를 받는다. (3) 앞의 둘은 대조 실험 없이 실패 메시지에서 원인을 단정했다. 셋째는 방법이 틀렸다 — seccomp 필터가 여럿이면 ERRNO 가 TRACE 보다 우선하므로 `strace --seccomp-bpf` 는 Docker 필터가 막은 호출에서 멈추지 않는다. 일부러 일으킨 거부가 기록되는지 보는 양성 대조가 없었다.
- **대응**: (1) `alpha-eval` 에 fusectl 을 잠시 마운트해 해당 연결 (dev 0:398 · 소유 uid 1100, 보이는 연결은 내 것 둘뿐) 을 abort 했다. 프로세스 종료를 확인하고 마운트를 풀었다. (2) 사용자에게 보고했고 이미지는 남겼다 (삭제는 승인 대상).   - 5 step 간 파라미터 이동량 (‖Δθ‖/‖θ‖, DCP 직접 로드)은 200→205 6.1e-4 ~ 275→280 6.6e-4 로 붕괴 전·중·후가 같다. 라우터 0 (동결 확인), norm ≈ 0. **정정 (2026-10-16 12:40)**: 재학습 `teacher_codemath2` 의 정상 구간 10→15 (lr 은 이미 5e-6) 는 9.4e-5 로 **6.5배 작다**. Muon 은 모멘텀을 직교화하므로 걸음 크기가 기울기 크기에는 둔감하지만 유효 랭크에는 비례한다 — 잡음이 많은 고랭크 기울기일수록 걸음이 커진다. 따라서 s1r5 는 step 200 에 이미 초반의 6.5배로 걷고 있었고, 신호가 희소·손상될수록 걸음이 커지는 되먹임이 성립한다. 재학습 추적 결과 (2026-10-18): 25→30 2.3e-4 → 100→105 4.8e-4 → 200→205 6.0e-4 → 275→280 6.3e-4 로 **정상 런도 같은 값에 도달** — 걸음 크기는 학습 진행에 따른 자연 증가이며 붕괴를 가르는 지표가 아니다 (H2 최종 기각). 붕괴를 가르는 것은 같은 걸음에서 토큰 확률이 얼마나 변하는가(민감도)다.
  - 기각: 투기 디코딩(꺼짐) · 2 에폭 재방문(142~170 깨끗) · 길이 자체(25K 구간 KL 0.0019) · refit 실패(57회 정상, 점진 상승) · 형식 오류(증상) · 생성기 퇴행 · 라우팅 기록 누락 · 파라미터 이동 급증.
- **남은 가설**: 정책이 "같은 크기의 작은 가중치 변화(또는 엔진 수치 차이)가 샘플 토큰의 logprob 를 크게 바꾸는" 민감한 영역으로 들어갔다 — GDN 재귀 상태가 긴 시퀀스에서 작은 파라미터 차이를 증폭하는 경로가 유력 (10-06 의 "오차가 생성 위치를 따라 커짐" 과 같은 기전, 이번엔 수치가 아니라 민감도). 감점이 만든 급격한 길이 붕괴(entropy 최저 0.75, 발생 시점 일치)가 그 영역으로 밀어넣은 것으로 본다 (사용자 가설의 정밀화).

- **기전 (확인된 범위)**: 파라미터 걸음은 일정한데 **토큰 확률 공간에서의 step 당 변화가 특정 문맥에서 10 nats 이상**으로 커졌다 (정책의 출력 민감도 상승). async 는 나이 1~2 의 샘플을 R3 재생으로 학습하므로, 그 샘플의 희소 토큰이 현재 가중치에서 "불가능" 이 되어 threshold 2 마스킹(최대 39%)·TIS 절단·유효 토큰 감소(grad norm 10배)로 이어지고, 손상된 신호가 드리프트를 더 키웠다. 민감도 상승의 유발 조건은 감점이 만든 급격한 분포 이동(길이 26K → 6K, entropy 최저 0.75 뒤 0.9~1.0 으로 반등, 희귀 토큰 비율 2% → 3.4%) 이다. 생성 중 refit(`in_flight_weight_updates: true`, 상태 재계산 없음)이 섞인 상태를 만들 가능성은 남지만, 궤적이 refit 을 넘는 비율(p95 궤적 시간/step 시간)은 71~100 구간 2.1배·붕괴 구간 1.3~1.5배·STEM 1.2~1.7배라 그것만으로는 설명되지 않는다 (GPU 창에서 `in_flight_weight_updates` 끄고 마스킹 비교로 확정 가능).
- **교훈**: (1) 감시 지표에 `policy_kl_error`·마스킹 수·KL 두 방향의 비를 넣는다 — gen KL 만 보면 0.004 로 평온해 보인다 (cron 에 반영, 2026-10-16). (2) 보상 설계를 런 중간에 바꾸지 않는다; 바꾸면 세기는 논문 상대값(0/1 보상이면 감점 0.5)으로, 처음부터. (3) 드리프트가 빨라지는 구간(entropy 급변·길이 급변)에서는 staleness 를 1 로 줄이거나 lr·KL 앵커로 속도를 제한한다 — Muon 에서는 grad norm 이 아니라 ‖Δθ‖(체크포인트 쌍으로 측정)가 걸음의 지표이고, 잡음 기울기는 걸음을 키운다. (4) 체크포인트 keep-2 는 최고 구간을 지운다 — 25 step 마다 하드링크 보존. (5) 학습 중 샘플(train_data 덤프 또는 샘플별 jsonl)이 없으면 사후 분석이 리플레이 버퍼(18 GB/ckpt)에만 의존한다. (6) in-loss 마스킹은 증상을 숨긴다 — 마스킹이 1% 를 넘으면 멈추고 본다.

**대응**: 운영 클러스터가 떠 있는 노드에서는 NeMo-RL pytest 를 돌리지 않는다 — 클러스터가 비어 있을 때만 돌린다. CPU 단위 테스트는 `CUDA_VISIBLE_DEVICES=""` 로 GPU 를 가린다.
운영 런이 쓰는 venv 도 건드리지 않는다 — pytest 는 scratchpad 의 별도 venv 에 드라이버 venv 의 site-packages 를 `.pth` 로 이어 붙여 쓴다.

**재발 (2026-10-08 21:3x, `--noconftest` 로도 붙음)**: 도구 teacher 런 중에 `--noconftest -k noncolocated` 로 `tests/unit/algorithms/test_grpo.py` 를 돌렸다.

액터는 `num_cpus=0` 이고 fixture 정리 때 지워졌다. 런은 영향이 없었다 (36/400 스텝, KL 0.0013).
- **격리 방법**: Ray 를 쓰는 테스트 모듈은 `RAY_ADDRESS=local RAY_TMPDIR=$(mktemp -d /tmp/rut.XXXX)` 로 새 로컬 Ray 에서 돌린다.
  `RAY_ADDRESS=local` 이면 새 인스턴스를 띄운다 (`ray/_private/services.py:705-708`). `RAY_TMPDIR` 는 소켓 경로 길이 제한(107자) 때문에 짧은 `/tmp` 경로를 쓰고 끝나면 지운다.
